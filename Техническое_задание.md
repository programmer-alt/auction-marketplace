## 1. Цель проекта

Создать платформу для проведения аукционов с возможностью:

- Размещения лотов продавцами
- Размещения ставок покупателями
- Оплаты через Stripe
- Просмотра истории транзакций
- Real-time обновления ставок через WebSocket
- Автоматического завершения аукционов по времени
- Защиты от злоупотреблений (rate limiting, CSRF, валидация)

## 3. Структура базы данных (Prisma Schema)

```prisma
model User {
  id        Int       @id @default(autoincrement())
  email     String    @unique
  password  String
  name      String?
  balance   Decimal   @default(0) @db.Decimal(10, 2)
  auctions  Auction[] @relation("SellerAuctions")
  bids      Bid[]
  payments  Payment[]
  createdAt DateTime  @default(now())
}

model Auction {
  id           Int        @id @default(autoincrement())
  title        String
  description  String?
  imageUrl     String?
  startingPrice Decimal    @db.Decimal(10, 2)
  currentPrice Decimal    @db.Decimal(10, 2)
  sellerId     Int
  seller       User       @relation("SellerAuctions", fields: [sellerId], references: [id])
  winnerId     Int?
  winner       User?      @relation("WinnerAuctions", fields: [winnerId], references: [id])
  status       AuctionStatus @default(ACTIVE)
  endsAt       DateTime
  bids         Bid[]
  payments     Payment[]
  createdAt    DateTime   @default(now())
}

model Bid {
  id        Int      @id @default(autoincrement())
  auctionId Int
  auction   Auction  @relation(fields: [auctionId], references: [id])
  userId    Int
  user      User     @relation(fields: [userId], references: [id])
  amount    Decimal  @db.Decimal(10, 2)
  createdAt DateTime @default(now())
}

model Payment {
  id              Int            @id @default(autoincrement())
  userId          Int
  user            User           @relation(fields: [userId], references: [id])
  auctionId       Int
  auction         Auction        @relation(fields: [auctionId], references: [id])
  amount          Decimal        @db.Decimal(10, 2)
  stripePaymentId String?
  status          PaymentStatus  @default(PENDING)
  createdAt       DateTime       @default(now())
}

enum AuctionStatus {
  ACTIVE
  COMPLETED
  CANCELLED
}

enum PaymentStatus {
  PENDING
  COMPLETED
  FAILED
}
```

## 4. API Endpoints

### Аутентификация

- `POST /api/auth/register` - Регистрация (с rate limiting)
- `POST /api/auth/login` - Вход (с rate limiting)
- `GET /api/auth/me` - Текущий пользователь (обязательная аутентификация)

### Аукционы

- `GET /api/auctions` - Список аукционов (опциональная аутентификация)
- `GET /api/auctions/:id` - Детали аукциона (опциональная аутентификация)
- `POST /api/auctions` - Создать аукцион (только продавец, обязательная аутентификация)
- `PUT /api/auctions/:id` - Обновить аукцион (только продавец)
- `DELETE /api/auctions/:id` - Удалить аукцион (только продавец)

### Ставки

- `POST /api/auctions/:auctionId/bids` - Сделать ставку (обязательная аутентификация)
- `GET /api/auctions/:auctionId/bids` - История ставок (публичный доступ)

### Платежи

- `POST /api/payments/create-intent` - Создать Payment Intent (обязательная аутентификация)
- `POST /api/payments/webhook` - Webhook Stripe (публичный, без аутентификации)
- `GET /api/payments/history` - История платежей (обязательная аутентификация)

## 5. Архитектура и middleware

### Безопасность

1. **Security Headers Middleware** — кастомный middleware `securityHeaders.ts`, устанавливающий современные security HTTP-заголовки:
   - **Content-Security-Policy (CSP)** с конфигурацией, разрешающей ресурсы только с доверенных источников (`'self'`, `https:`, `data:`), блокирующая inline-скрипты и eval в production.
   - **X-Frame-Options: DENY** — запрет встраивания страницы в iframe.
   - **X-Content-Type-Options: nosniff** — предотвращение MIME-sniffing.
   - **Referrer-Policy: strict-origin-when-cross-origin** — контроль передачи referrer.
   - **Permissions-Policy** — ограничение доступа к API браузера (камера, микрофон, геолокация и т.д.).
   - **Strict-Transport-Security (HSTS)** — принудительное использование HTTPS в production (max-age=1 год, includeSubDomains).
   - Конфигурация CSP адаптируется для development (разрешает `unsafe-inline`, `unsafe-eval`, локальные WebSocket) и production (включает `upgrade-insecure-requests`, `block-all-mixed-content`).
2. **Helmet** — устанавливает security HTTP-заголовки (используется как fallback, если кастомный middleware не применяется).
3. **HPP** — защита от параметрического загрязнения.
4. **CORS** — настройка кросс-доменных запросов с явным указанием доверенных доменов.
5. **CSRF защита** — middleware для защиты от CSRF-атак на state-changing запросы.
6. **Rate Limiting**:
   - Глобальный лимит: 100 запросов в минуту на IP (с использованием Redis, fallback на LRU-кэш в памяти при недоступности Redis).
   - Лимиты на аутентификацию: 5 попыток входа и 10 регистраций за 15 минут с одного IP.
   - WebSocket rate limiting:
     - Ограничение подключений: максимум 10 подключений с одного IP за 60 секунд.
     - Ограничение ставок: 1 ставка в 5 секунд на пользователя.
     - Реализация через Redis с ключами вида `ws:rate_limit:{userId}` и fallback на memory store.
7. **Аутентификация**:
   - Двухуровневая система токенов:
     - Access token: короткоживущий JWT (15 минут), передаётся в заголовке `Authorization: Bearer <token>`.
     - Refresh token: долгоживущий JWT (7 дней), хранится в HTTP-only, Secure cookie.
   - Эндпоинт `/api/auth/refresh` для обновления пары токенов.
   - Хранение токенов только в памяти (Zustand store), без использования localStorage для защиты от XSS.
   - Механизм blacklist в Redis для инвалидации токенов при выходе (токены добавляются в чёрный список до истечения срока действия).
   - Проверка blacklist при каждой аутентификации через middleware.
   - Обязательная аутентификация (`authMiddleware`) для защищённых маршрутов.
   - Опциональная аутентификация (`optionalAuthMiddleware`) для маршрутов, где пользователь может быть неавторизован, но если токен предоставлен — он валидируется.
8. **Валидация**:
   - Все входящие данные валидируются с помощью Zod на стороне бэкенда.
   - Формы на фронтенде также используют Zod для предварительной валидации.
9. **Stripe Webhook** — проверка подписи входящих запросов с использованием секрета Stripe.
10. **WebSocket Rate Limiting** — ограничение частоты событий (например, ставок) через Redis на основе пользователя/IP.
11. **Мониторинг и алертинг** — логгирование подозрительной активности (например, множество ставок) и отправка алертов.

#### Исправления уязвимостей OWASP Top 10

В проекте устранены следующие категории уязвимостей OWASP Top 10:

- **A02: Cryptographic Failures** — все пароли хешируются с помощью bcrypt, JWT подписываются с использованием секретного ключа, передача данных осуществляется по HTTPS (в production), чувствительные данные (токены, платежные реквизиты) никогда не логируются.
- **A03: Injection** — использование Prisma ORM с параметризованными запросами предотвращает SQL-инъекции; валидация входных данных через Zod исключает NoSQL-инъекции и инъекции команд.
- **A07: Identification and Authentication Failures** — реализована двухфакторная аутентификация через JWT + refresh token, rate limiting на попытки входа, блокировка учетных записей при множественных неудачных попытках, сессии управляются через HTTP-only cookies, пароли соответствуют политике сложности.
- **A09: Security Logging and Monitoring Failures** — внедрено централизованное логирование ошибок и подозрительных событий (множественные ставки, попытки подбора паролей), интеграция с Sentry для мониторинга, алертинг при аномальной активности.

Дополнительно реализованы security headers (см. пункт 1), которые защищают от атак типа clickjacking (X-Frame-Options), MIME-sniffing (X-Content-Type-Options), XSS (CSP), а также обеспечивают безопасную передачу данных (HSTS).

### Real-time коммуникация

- **Socket.io** с Redis адаптером для горизонтального масштабирования.
- События:
  - `bid:created` — новая ставка на аукционе.
  - `auction:updated` — обновление данных аукциона.
  - `auction:completed` — завершение аукциона.

### Фоновые задачи

- **Bull** — очередь задач на основе Redis.
- Задачи:
  - Завершение аукциона по истечении времени `endsAt`.
  - Отправка уведомлений победителю и продавцу.

### Кэширование

- Redis используется для кэширования:
  - Списки аукционов (TTL 60 секунд).
  - Отдельные аукционы (TTL 60 секунд).
- Инвалидация кэша при изменении данных.

### Тестирование

- **Vitest** — unit и интеграционные тесты.
- **Supertest** — HTTP тестирование эндпоинтов.
- Тестовое окружение использует отдельную базу данных и Redis.

## 6. Основные функции

1. **Регистрация/Вход** — JWT токены, хеширование паролей bcrypt.
2. **Создание лота** — форма с валидацией, загрузка изображений (URL), установка времени окончания.
3. **Просмотр лотов** — пагинация, фильтрация по статусу, поиск, сортировка.
4. **Размещение ставок** — real-time обновление через WebSocket, проверка на превышение текущей цены.
5. **Завершение аукциона** — автоматически по времени через очередь задач, определение победителя.
6. **Оплата** — интеграция Stripe Checkout, создание Payment Intent, обработка вебхуков.
7. **История** — личный кабинет: мои аукционы, мои ставки, платежи.
8. **Таймер аукциона** — обратный отсчёт на странице аукциона с возможностью паузы/возобновления (демо-режим).
9. **Защита от злоупотреблений** — rate limiting, CSRF, валидация, безопасные заголовки.

## 9. Безопасность (Security Considerations)

### Реализованные меры защиты

#### 1. Security Headers Middleware
В проекте реализован кастомный middleware `securityHeaders.ts`, который устанавливает современные security HTTP-заголовки:

- **Content-Security-Policy (CSP)** – политика безопасности контента, ограничивающая источники загрузки ресурсов. Конфигурация по умолчанию:
  - `default-src 'self'` – разрешает загрузку только с того же origin.
  - `script-src 'self' 'unsafe-inline' 'unsafe-eval'` – в development разрешает inline-скрипты и eval для совместимости; в production эти директивы должны быть удалены.
  - `style-src 'self' 'unsafe-inline'` – разрешает inline-стили.
  - `img-src 'self' data: https:` – изображения с любых HTTPS источников и data-URI.
  - `connect-src 'self' http://localhost:* ws://localhost:*` – WebSocket и API вызовы к локальному серверу.
  - `object-src 'none'`, `frame-src 'none'`, `frame-ancestors 'none'` – блокировка встраивания через `<object>`, `<embed>`, `<iframe>`.
  - В production автоматически добавляются `upgrade-insecure-requests` и `block-all-mixed-content`.

- **X-Frame-Options: DENY** – полный запрет на отображение страницы во фрейме (защита от clickjacking).

- **X-Content-Type-Options: nosniff** – предотвращение MIME-sniffing, браузер будет следовать указанному Content-Type.

- **Referrer-Policy: strict-origin-when-cross-origin** – referrer передаётся только при переходе внутри того же origin, при кросс-доменных запросах передаётся только origin (без пути).

- **Permissions-Policy** – ограничение доступа к API браузера:
  - `camera=()`, `microphone=()`, `geolocation=()` – полный запрет.
  - `fullscreen='self'` – разрешение fullscreen только в том же origin.

- **Strict-Transport-Security (HSTS)** – принудительное использование HTTPS в production (max-age=31536000, includeSubDomains).

#### 2. Исправления уязвимостей OWASP Top 10
Проект устраняет следующие категории OWASP Top 10:

- **A02: Cryptographic Failures** – пароли хешируются с помощью bcrypt, JWT подписываются секретным ключом, передача данных по HTTPS, чувствительные данные не логируются.
- **A03: Injection** – использование Prisma ORM с параметризованными запросами предотвращает SQL-инъекции; валидация входных данных через Zod исключает NoSQL-инъекции и инъекции команд.
- **A07: Identification and Authentication Failures** – двухфакторная аутентификация через JWT + refresh token, rate limiting на попытки входа, блокировка учётных записей при множественных неудачных попытках, сессии через HTTP-only cookies.
- **A09: Security Logging and Monitoring Failures** – централизованное логирование ошибок и подозрительных событий, интеграция с Sentry, алертинг при аномальной активности.

#### 3. Дополнительные security middleware
- **CSRF защита** – middleware `csrf.ts` для защиты state-changing запросов.
- **Rate Limiting** – глобальный и аутентификационный лимиты, WebSocket rate limiting.
- **Аутентификация** – двухуровневая система токенов с blacklist в Redis.
- **Валидация** – Zod на фронтенде и бэкенде.

### Рекомендации для production

1. **HTTPS** – обязательное использование TLS/SSL на всех окружениях. В production следует включить HSTS с preload (после тщательного тестирования).
2. **CSP в production** – убрать `'unsafe-inline'` и `'unsafe-eval'` из `script-src`, переместив все скрипты во внешние файлы. Использовать nonce или хэши для inline-скриптов при необходимости.
3. **Регулярный аудит зависимостей** – выполнять `npm audit` и использовать инструменты типа Snyk для сканирования уязвимостей в зависимостях.
4. **Сканирование кода (SAST)** – интегрировать статический анализ безопасности в CI/CD (например, SonarQube, ESLint security правила).
5. **Мониторинг и алертинг** – настроить оповещения о подозрительной активности (множественные неудачные логины, частые ставки, попытки инъекций).
6. **Резервное копирование и восстановление** – регулярные бэкапы базы данных и Redis, тестирование процедуры восстановления.
7. **Обновление зависимостей** – поддерживать актуальные версии всех пакетов, особенно security-патчей.
